Breaking a lock

Every day at work, I lock up my laptop for the night (working with clients means top-secret data!) The lock is a standard 3-digit lock, inset into a cabinet. I always shuffle it after, but I've realized my shuffling strategy isn't the most sophisticated: I just give the digits a push or two, with one finger per digit. This results in a shuffle where each digit has been displaced around the same amount. So I want to figure out whether the original passcode is recoverable from just seeing my shuffled versions. We'll come up with an algorithm to produce an estimate of the original passcode based on a collection of shuffled passcodes. If this algorithm is successful, I'll have to change my shuffling strategy!

First, I have to model my shuffle strategy. Let's say the shuffle is defined by three numbers \(p_1, p_2, p_3\), where this is the amount I rotated each digit. Let's also assume \(1\leq p_i\leq 10\). We'll model the likeelihood of a shuffle in the following way: the likelihood depends only on \(\max p_i - \min p_i\). So shuffles where \(p_1 = p_2 = p_3\) is most likely. Then if \(\max p_i - \min p_i = 1\), we'll say this is only slightly less likely - let's say 80% as likely. Given this approximation, we'll say \(l(p_1, p_2, p_3) \propto .8^{\max p_i - \min p_i}\).

Let's say we've observed \(n\) passwords, \(y_1^{(i)}y_2^{(i)}y_3^{(i)}\). Under this model, the negative log-likelihood of password \(x_1x_2x_3\) is proportional to \(\sum_{i=1}^n(\max(p_1^{(i)}, p_2^{(i)}, p_3^{(i)}) - \min(p_1^{(i)}, p_2^{(i)}, p_3^{(i)}) )\), where \(p_j^{(i)} = y_j^{(i)} - x_j \text{ mod } 10 \). Turns out the choice of \(80\%\) doesn't matter - ultimately, we are just minimizing the total amount we deviate from the digits having been equally rotated.

Let's throw this minimization problem into a computer program. There are a total of \(1000\) possible passcodes, so we can use a brute-force approach.

Turns out this algorithm has a flaw. Let's say the first digit is \(3\), and I shuffle it to a \(4\). Then \(p_1 = 1\), but it's much more likely that it is \(11\). This can throw off the spread term quite a bit. To account for this, I add some flexibility: for every term in the sum, I'll allow the possibility of a wrap-around: you may add \(10\) to any subset of \(\{p_1, p_2, p_3\}\), and assign the minimum spread of any of these \(8\) possiblities as the term in the sum. What this is saying is that we don't know of \(p_1\) is \(1\) or \(11\): take the value that would benefit the objective the most. This makes the brute-force seven times slower, but it's still extremely fast!

This actually helped quite a bit! Below we plot the rank of the true password as we give our algorithm more data - up to \(18\) datapoints.

The true password is elusive. We see that with the wraparound addition, the rank of the true password became as low as four. However, it seems that we have converged to rank \(42\) with both algorithms. While I'm glad my shuffle algorithm isn't decodable (yet!), I feel we can do better.

What I notice is that there are some outliers that are driving the algorithms away from the true password. While we could allow the algorithm to "drop" two outliers - this actually helps the rank - let's look more closely at these outliers. What I find is that in these cases, it looks like two of the \(p_i\)'s are close to eachother, but the other is way off. And then it comes back to me - sometimes, when I am shuffling, my index finger slips. This would explain this pattern exactly!

Let's modify the algorithm to account for this behavior. For shuffles that seem like outliers, let's allow the objective to fall back to computing the minimum spread over pairs of digits. But, we must also add a penalization for how many times the algorithm fell back! The parameters we can control here are: the threshold at which the algorithm falls back, \(\tau\), and the penalization constant, \(\lambda\). Here's the objective for a single term[1]: we compute the wraparound distance. If it's more than \(2\), we compute the fallback wraparound: we compute the wraparound for all pairs of digits, and take the minimum. Then if we had to fallback for this shuffle, we add \(\lambda = 10\) to the objective.

Turns out a threshold of \(1\) is too strict: this algorithm is worse than our simple ones. However, with \(\tau = 2\) and \(\lambda \geq 8\), the true password jumps to rank \(1\) (although tying with nine other passwords, to my dissapointment).

Yay! We've constructed an algorithm that recovers the true password (ignoring ties!) This was a fun problem because the first algorithm I came up with was far from optimal, but we got there, eventually. I'm not done yet though - I'll keep collecting data until I'm able to eliminate the tie.

[1] I didn't include the mathematical objective in the main body of this blog because it is quite ugly. For completeness, here it is:

Recall that \(p_j^{(i)} = (y_j^{(i)} - x_j) \bmod 10\) for each string \(i = 1,\dots,n\) and digit position \(j \in \{1,2,3\}\). For a finite set of numbers \(A\) with \(|A| = m\), define the wraparound distance

\[ d(A) = \min_{s \in \{0,1\}^m} \left[\max_j (a_j + 10 s_j) - \min_j (a_j + 10 s_j)\right] \]

where \(a_j\) ranges over the elements of \(A\). Then, fixing a threshold \(\tau\), the score for string \(i\) is

\[ \text{score}_i(x) = d(\{p_1^{(i)}, p_2^{(i)}, p_3^{(i)}\}) \]

if \(d(\{p_1^{(i)}, p_2^{(i)}, p_3^{(i)}\}) \leq \tau\), and otherwise

\[ \text{score}_i(x) = \min_{j \neq k} d(\{p_j^{(i)}, p_k^{(i)}\}) \]

The fallback count is

\[ F(x) = \sum_{i=1}^n \mathbb{1}\left[d(\{p_1^{(i)}, p_2^{(i)}, p_3^{(i)}\}) > \tau\right] \]

giving the regularized objective

\[ J_\lambda(x_1,x_2,x_3) = \sum_{i=1}^n \text{score}_i(x) + \lambda\,F(x) \]

which we minimize over \(x_1, x_2, x_3 \in \{0,\dots,9\}\).
